# ADR 0013: The control plane is generated; the plumbing is hand-written

**Status:** Accepted; supersedes ADR 0010
**Date:** 2026-09-23

## Context

tinyactors-test does not bind core by hand. `mise run api` in core turns
the annotated header into `tinyactors.api.json`, a description of every
function and type that includes ownership, buffers, releases, handles and
value models. The test host's generator reads only that file and produces its
JSON-RPC surface: about 1,100 lines of generator and 75 lines of policy
produce 8,159 lines of C that bind 53 functions and 89 types. Hand-written
code covers only what cannot be generated: the adapters that implement core's
callback interfaces, a small runtime, and the actor enumeration.

The same split suits the addon. Most of what JavaScript calls maps directly
to a core function, such as defining, spawning, inspecting, capturing,
retiring and finding. Generating those calls:
- makes it impossible for the addon to store facts that core owns
  (ADR 0001);
- carries core changes (tinyactors-core ADRs 0054–0059) to JavaScript
  without hand edits;
- makes the addon fail its build when a new core item has no decision.

Some things cannot be generated in either design:
- scheduling (ADRs 0005–0007);
- the callback interfaces: router, directory, I/O processors, invokers, log
  sink, allocator and data model;
- value boxes (ADR 0011);
- enumeration (ADR 0003);
- event-name interning (ADR 0004).

These are the plumbing.

The test host's generator is not reused. Its plan makes decisions that belong
to JSON-RPC: member keys, JSON schemas, flattening into JSON objects, and jq
fallbacks for value models. Its emitter writes jq calls. A Node-API binding
decides other things: positional arguments, `napi_wrap` handles, value boxes
and generation-checked actor IDs. The contract the bindings share is the API
description, not a generator.

## Decision

1. **The addon owns its generator.** `tinyactors-napi/mise/lib/napi` reads
   `tinyactors-core/include/tinyactors.api.json` and validates it against
   `tinyactors.api.schema.json`. Its only inputs are that description and the
   addon's policy (`bindings.rb`). tinyactors-test keeps its own generator.
   - **The output is checked in** as `src/gen/ta_napi.{c,h}`, with a header
     comment that marks it as generated and names its inputs. It is
     regenerated by `mise run bindings` and never edited by hand. A change to
     core's API therefore shows up as a reviewable diff of the binding, and
     the addon builds without running the generator. Core checks in
     `tinyactors.api.json` for the same reasons.
   - **Staleness fails the tests.** `mise run test` regenerates into a
     temporary directory and fails if the output differs from the committed
     files, naming the command that fixes it. A commit that changes the API
     description or the policy without regenerating does not pass.
2. **A policy file puts every function and type into exactly one category**
   (`tinyactors-napi/bindings.rb`):
   - **bound**: generated and callable from JavaScript;
   - **bound with a hook**: generated, and a hand-written hook runs after a
     successful call so the plumbing sees the change:
     - `ta_actor_spawn`, `ta_actor_load`, `ta_actor_reconstruct` and
       `ta_actor_prepare_replacement` put the new actor on the runnable
       queue for bootstrap;
     - `ta_actor_destroy` drops the actor's mailbox as dead letters, and
       `ta_actor_unload` does the same with reason `unloaded`;
     - `ta_actor_activate_replacement` moves the incumbent's waiting mail
       to the front of the replacement's mailbox (ADR 0005 point 12). Its
       hook takes the whole params struct (`actor: 'params'` in
       `bindings.rb`);
   - **plumbing-owned**: not callable from JavaScript, because calling it
     would bypass or break the scheduler. Each entry gives a reason. The
     initial list is:
     - `ta_actor_deliver`, `ta_actor_resume` and `ta_actor_publish_completion`
       (the pump);
     - `ta_system_dispatch_due` and `ta_system_set_time` (the clock);
     - `ta_system_set_external_event_router` and
       `ta_system_set_actor_directory` (installed at creation);
     - `ta_system_register_io`, `ta_system_register_invoker`,
       `ta_system_set_log_sink` and `ta_actor_report_invoke` (reached through
       hand-written JavaScript-facing registration);
     - `ta_system_create` and `ta_system_destroy` (ADR 0012);
     - `ta_system_visit_actors` (ADR 0003);
   - **overridden**: a hand-written codec or function replaces the generated
     one:
     - `ta_expression` carries JavaScript functions as
       `TA_EXPRESSION_HOST`;
     - `ta_actor_id` is carried as `(slot, generation)` (ADR 0002);
     - `ta_value` is carried as value boxes (ADR 0011);
     - `ta_address` (tinyactors-core ADR 0065) is carried as its text, a
       family and a name. Inputs are interned for the call, and outputs are
       read through `ta_address_view()`. JavaScript never holds a handle;
   - **skipped**: C-only utilities (`ta_arena_*`, `ta_tree_*`, retain and
     release helpers) and functions that can only be called from inside a
     callback (`ta_dm_host_*`), each with a reason.

   The generator fails when an item fits no category, when a bound item
   needs a skipped or plumbing-owned one, and when a policy entry matches
   nothing. This is the same discipline as tinyactors-test's `bindings.rb`.
3. **Calling convention.**
   - Arguments are positional in declaration order, and a `params` struct is
     flattened into positional arguments. No call builds a parameter object.
   - Outputs are returned: a single output as the value, several outputs as
     one object.
   - A result other than `TA_OK` throws a `TinyactorsError` whose `code` is
     derived from the enum symbol in the API description (ADR 0008).
4. **Reentrancy guard.** The plumbing sets a per-system "inside core" flag
   around every core call. Each generated entry point checks that flag and
   throws `reentrant` if it is set. Data-model, I/O and invoker callbacks
   can therefore run JavaScript but cannot call back into core
   (tinyactors-core ADR 0017).
5. **Handles.** A handle type in the API description becomes a `napi_wrap`
   whose finalizer calls the release function the description names (for
   example `ta_session_image_destroy`), as a safety net behind explicit
   destruction. `System` is plumbing-owned and follows ADR 0012.
   `Definition` is a thin wrapper around a `ta_definition_id` in a system.
6. **Specs use generated codecs.**
   - `ta_scxml_spec` and its types decode through generated struct codecs
     into one arena. They reject unknown members and report the path of any
     error.
   - The JavaScript builder (`statechart()`) emits this generated shape
     directly. There is no separate normalization step.
   - Byte formats go through `ta_definition_import` (tinyactors-core ADR
     0053).
7. **The generated layer is internal.** `index.js` loads it as a private
   module and builds `System`, `Actor`/`ActorId` and `statechart()` on top of
   it. It is not a public API, so it can change with core without a semver
   promise. Publishing a filtered raw layer would need its own ADR.
8. **Hand-written code is only plumbing:** mailboxes, ready and runnable
   queues, router, directory, pump, clock, adapters for callback interfaces,
   the JavaScript data model and value boxes, enumeration, event-name
   interning, hooks, the reentrancy guard, and the Node-API runtime used by
   generated code.

## Consequences

- A new core function breaks the addon's build until the policy
  classifies it. The regenerated binding is committed with the
  policy change, so review sees both. A core function that changes shape changes its generated
  binding, and `index.js` adapts in one place.
- The generated layer and tinyactors-test expose the same core functions
  (minus the plumbing-owned ones). Porting the scenario suite to run
  against the addon becomes practical.
- Generic decoding costs about one property read per struct field, and only
  where a struct is really passed (specs, addresses). Positional flattening
  keeps singular calls like `spawn` free of parameter objects. The busiest
  path (post, mailbox, deliver, resume, router) never goes through generated
  code.
- Two generators read the same description, one per binding target. That
  is accepted duplication: their targets need different plans.
- ADR 0010 is superseded. Its decisions about the null data model, codecs
  and identity still hold and are restated here or in ADR 0001. JavaScript
  no longer normalizes specs, and there is no hand-written spec decoder.
